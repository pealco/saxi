# Plotter routing research and evaluation

Current implementation: [SIMD Wasm production routing](routing-simd-production.md) now refines the prepared route in the browser and CLI when sorting is enabled. It preserves directed strokes and nearby order, uses a bounded search, and requires five net modeled seconds to select a candidate. The historical experiments below retain their original baselines and measurements.

Latest follow-up: [optimized JS, scalar Wasm and SIMD Wasm](routing-wasm-experiment.md). All three are implemented and benchmarked with worker startup, compilation and transfer included. Across 528 timed runs, fixed-effort routes match exactly and all physical audits pass. With a five-second allowance, optimized JS saves 5.9–20.9 net seconds versus cheap search on nine of 14 cases. Scalar Wasm is faster, but adds at most 2.28 seconds per-case median beyond optimized JS; SIMD adds no robust five-second gain. Two-second trials also fail to establish a five-second incremental Wasm gain. All 1,116 settings combinations pass for each port. That experiment initially left production routing unchanged; the subsequent integration is described above.

The preceding [large-neighborhood experiment](routing-neighborhood-experiment.md) introduced regret-based ruin/recreate and found six robust multi-second wins on 42 fresh large drawings, including planning. The new runtime experiment accelerates that same algorithm; it does not introduce another search heuristic.

The preceding [adaptive beam experiment](routing-adaptive-experiment.md) found no additional five-second advantage over cheap search. The new reconstruction method changes groups of 32 route positions together and preserves the same strict physical contract.

**What is actually implemented**

The experiments now include **bounded, physically constrained rollout-beam and large-neighborhood optimizers**, as well as the earlier hybrid classical heuristics. [The reconstruction implementation](../tools/neighborhood-routing.mjs) combines related/contiguous removal, candidate-limited regret-2 insertion, annealing acceptance and final local refinement; it also contains an exact-window dynamic-programming control. These are concrete implemented techniques, without a trained neural policy. [The earlier rollout implementation](routing-rollout-experiment.md) adapts Limited Rollout Beam Search's expansion → short rollout → retain reached states procedure using a deterministic heuristic policy and Saxi motion costs. Production now adds the SIMD reconstruction hybrid after the existing sorter and joining steps.

The following table and historical results describe the earlier, more permissive hybrids. Their segment-coverage checks allow direction, seam, contact, and crossing-order changes that the new optimizer rejects. These are different feasible sets; compare the new report's constraint audit alongside timing.

| Implemented technique | What the code actually does | Code and limits |
| --- | --- | --- |

The classical background includes [Croes's TSP local-improvement work](https://doi.org/10.1287/opre.6.6.791), the stack-based Euler traversal explained in [NetworkX's algorithm guide](https://networkx.org/nx-guides/content/algorithms/euler/euler.html), and the perturbation/local-search/acceptance framework in [Lourenço, Martin, and Stützle's Iterated Local Search chapter](https://iridia.ulb.ac.be/~stuetzle/publications/LouMarStu10.pdf). These identify algorithm families; the code is an independent implementation adapted to reversible plotter strokes, not a reproduction of those authors' complete experimental solvers. The four fixed perturbations, greedy odd-vertex pairing, straightness preference, sampled seams, and candidate combinations are choices made for this experiment.

The names in the results refer to concrete combinations:

- **Quick direction/order refinement (`joint-states`):** greedy order → time-based 2-opt → direction/seam DP → another 2-opt/DP refinement, keeping the faster complete plan.
- **Targeted relocation (`relocate`):** greedy order → time-based 2-opt → single-stroke relocation. It does not run the seam DP or the four perturbations.
- **Contour refinement (`iterated-search`):** the direction/seam route above, followed by four perturb-and-refine attempts. The movable starting points are particularly useful for closed contours.
- **Connected-drawing refinement (`traversals`):** each of four Euler decompositions → greedy trail ordering → 2-opt → direction/seam DP → full motion-plan comparison.
- **Full search (`search-all`):** an outer portfolio testing seven recipes both before and after configured tolerance joining. This is the expensive “try everything” benchmark, not a separately trained or more sophisticated routing solver.

Each recipe uses the current drawing settings. Eligible exact joins and the user's configured tolerance merge are applied at the placement being tested. Final geometry checks and full Saxi motion plans decide which candidates are eligible; among candidates within 1% of the fastest estimated plot, selection prefers fewer pen contacts and never exceeds the current estimated plot time. The inner 2-opt/relocation searches only optimize pen-up transitions; smooth traversal uses a local angle heuristic. Full motion scoring is therefore essential: those local objectives do not jointly optimize all drawing, cornering, travel, and servo effects.

The small-instance subset dynamic program and exhaustive searches in the tests are **correctness/optimality references**, not the algorithms used on large drawings. The older recipes below have no time-budget controller or trained selector. The new rollout experiment has a cooperative search deadline and bounded effort, but no guarantee that searching will pay for itself on every drawing. Beam search and the older candidate portfolios remain in the offline `tools/` scripts. Production retains `optimize-paths` preprocessing and adds the bounded SIMD reconstruction hybrid through `src/massager.ts`.

**Measured results**

Connected strokes offer the largest improvement found so far. On synthetic grids, choosing continuous trails with fewer slow corners reduces Saxi's estimated total plotting time by about 38%. Connected loop chains improve by 17%, and separate closed contours by 6.6%. Scattered strokes improve by 2.7%. These are motion-plan estimates, including drawing, travel, lifting, lowering, and returning home; they are not measured hardware speedups.

The practical direction is to build continuous strokes first, optimize their directions and starting points, and compare complete motion plans. Preserve the original order as a candidate. In an already well-ordered grid, the current greedy sorter increases estimated time from 79.31 to 128.56 seconds. The best tested candidate takes 78.56 seconds and reduces lift/drop cycles from 32 to 28. Most of the apparent 39% saving versus the greedy result is recovering that regression.

Counting planning time favors targeted refinements over running every experiment. On a 2,000-stroke drawing, the full search takes 37.3 seconds to save 31.6 plotting seconds: a loss for one copy. Calling its winning relocation recipe directly takes about 2.6–2.8 seconds for the same estimated plot duration. Against a quicker 1.4–1.5-second refinement, however, that extra polishing is roughly a tie for one copy and saves about 11 additional seconds over ten reused copies. The measurements and limits are detailed below.

The experiments live in [benchmark-physical-routing.mjs](../tools/benchmark-physical-routing.mjs) and [physical-routing.mjs](../tools/physical-routing.mjs). This historical experiment used the existing sorter as its baseline; the settings evaluation described below added two preprocessing fixes. Run the physical evaluation with `npm run --silent eval:routing:physical > /tmp/physical-routing.json`. Run the earlier route-order evaluation with `npm run --silent eval:routing > /tmp/routing.json`.

The grid improvement is mainly about motion while drawing. For seed 17, drawing time falls from 106.24 to 64.12 seconds, travel from 11.39 to 8.77, and servo time from 7.92 to 6.72. Both drawings contain exactly the same segments. Long straight continuations avoid repeated corner slowdowns. A simple count of very sharp turns misses this: 90-degree turns matter even when no turn exceeds 120 degrees.

For the endpoint graph used here, a connected component with `o` odd-degree vertices needs `max(1, o/2)` trails without repeating or adding edges. The Euler decomposition attains this count; dots remain separate events. That guarantee concerns trail count, not total time. Local straightness does not guarantee the smoothest completed trail because circuit splicing changes junction transitions. Trying several traversals improved loop-chain savings from about 15% to 17%. For separate closed contours, movable starting points contribute much more than restarts alone.

On this machine the four-traversal experiment takes roughly 2 ms for loop chains and 7 ms for grids. Contour optimization with restarts takes roughly half a second for 300 loops. These are single-run algorithm timings, not repeated performance measurements; selecting the best among all evaluated methods costs their combined search time. The 5,000-edge chain reduces from two trails to one and from 7.70 to 6.70 estimated seconds. Spatial candidate lists would be needed before using the quadratic route search indiscriminately on much larger disconnected drawings.

**Joining needs a stricter contract than proximity.** The current `optimize-paths` merge, called from [massager.ts](../src/massager.ts), drops the beginning of the next path while its points remain within the join radius. With the default 0.5 mm radius, the microdetail fixture loses small bends. A fixture of 100 deliberately separated dashes becomes one continuous stroke; 20 repeated dots become one pen contact. These are changes to the drawing, so their time savings are excluded from the strict comparison. The new exact join keeps all original segments and preserves repeated dots, including segment multiplicity.

Even identical segment coverage does not promise identical ink deposition. Reversing a stroke, moving a seam, changing crossing order, or eliminating a stop can affect the physical mark. The benchmark permits reversal and reordering. Its state optimizer can lock directions and seams, and separate optimizer calls preserve group boundaries, but the complete experimental pipeline does not yet enforce layer, direction, or order constraints. The graph uses supplied endpoints only; it does not split interior intersections. These restrictions must be resolved when integrating it into production.

**Recent research: implementation status**

These citations informed possible directions and how to frame the physical problem. The historical gains above came from the classical hybrids. LRBS now also has a separate, explicitly adapted implementation and benchmark:

The near-term gain comes from representing the physical problem correctly. A neural solver adds training, inference, and distribution questions before addressing the geometry model. [COGS, a 2025 preprint](https://arxiv.org/abs/2508.08718), also reports realistic TSP distributions on which existing neural approaches perform poorly. Its relevance here is the need for varied drawing families and adversarial cases, rather than relying on uniformly scattered points.

The most useful further experiments are:

- **Search junction pairings directly.** At a shared vertex, choose which incoming stroke continues into which outgoing stroke, scoring the resulting acceleration and lift behavior. Optimize odd-vertex pairing and traversal together. Keep several good possibilities until their full trails can be evaluated.
- **Preserve artistic seams and direction.** Allow a set of acceptable start regions, locked winding, and protected stroke order. Disperse seams on repeated contours deterministically so a travel optimization does not align visible pen-down marks. AxiDraw's [official documentation](https://axidraw.com/doc/cli_api/#random_start) specifically describes aligned seam artifacts and randomized starts; its [reordering controls](https://axidraw.com/doc/cli_api/#reordering) also distinguish reversal and layer handling.
- **Generate continuous fills intentionally.** For artwork defined as a filled region, generate serpentine or connected contour paths inside that region from the start. This could remove many hatch lifts, where reordering alone shows almost no gain. Treat it as a drawing-generation choice with a pen-width and boundary model. It must not silently connect arbitrary dashes or independent line art.
- **Account for wet ink where contact occurs.** Associate drying times with recently drawn segments and schedule crossings accordingly. A lifted pen crossing a wet line is different from drawing through wet ink; clearance and paper deformation also matter. This requires a material model before claiming a quality improvement.
- **Allow retracing only as an explicit material choice.** A postman-style route can trade extra pen-down travel for fewer lifts, but repeated ink can darken, bleed, or damage paper. The current experiments add no retracing. Any future retracing mode needs a separate budget and visible preview of repeated coverage.

For production, use hard drawing constraints first; retain input order and the current route as feasible incumbents; generate a bounded set of exact-geometry candidates; then compare actual motion estimates and lift counts. Prefer fewer pen contacts when time is sufficiently close, with that tolerance made explicit. Keep seam quality, crossing order, and material constraints separate from geometric correctness. Physical validation should compare elapsed time and visible endpoints, corners, seams, and crossings using the actual pen/paper combination before making these experimental choices the default.

Checks cover exact edge and dot multiplicity, absence of phantom joins, every graph edge used exactly once, minimum trail count, nonmutation, near-coincident endpoints, duplicate edges, degenerate strokes, and finite motion estimates. Tiny direction/seam cases are compared against exhaustive enumeration. The earlier suite independently checks exact route costs against exhaustive permutations and orientations. All timing here comes from current `src/planning.ts`; communication overhead, servo settling beyond configured durations, slipping, drying, and ink appearance are uncalibrated.

**Planning time and repeated copies**

The relevant objective for a plan used `N` times is `P + N × T`, where `P` is planning time and `T` is plotting time per copy. Relative to the current planner, net time saved is `N × (T_current − T_candidate) − (P_candidate − P_current)`. With positive per-copy savings, the first strictly winning integer copy count is `floor(extra planning / per-copy saving) + 1`, bounded below by one. If a search costs more and finds no improvement, no number of copies recovers that cost. A tie is not a gain.

This amortization applies to Saxi's browser workflow: [usePlan](../src/ui.tsx) retains the plan, and the Plot button submits it again. Changing the drawing or most planning options creates a new worker and replans; changing only pen heights can reuse the route. Each separate `saxi plot` CLI invocation calls `replan` again. If every copy replans, the objective becomes `N × (P + T)`, so repetition does not change whether the method pays. More generally, `K` planning runs for `N` copies cost `K × P + N × T`. This also explains why repeatedly changing preview settings can make an expensive search unpleasant even when the eventual plot is faster.

The new [total-time benchmark](../tools/benchmark-routing-total-time.mjs) measures complete planning work rather than just the winning search stage. It includes current preprocessing, the existing greedy sorter, candidate search, raw and final geometry checks, candidate motion plans, fallback and selection, transferable construction, buffer enumeration, and local plan reconstruction. The `search-all` strategy tries seven algorithms at both placements. It shares preprocessing and relocation's 2-opt parent, and pays for every rejected alternative. Fixed strategies are separately measured alternatives that must be chosen in advance; selecting the fastest-looking row after running everything does not refund the other searches.

The benchmark preserves the earlier physical preference: among eligible routes within 1% of the fastest estimated plot, prefer fewer pen contacts, without exceeding the current plot time. A complete motion plan can fall back to the current route and still lose overall because computation has already been spent. The new analysis therefore reports that loss instead of treating fallback as free. These are time comparisons among routes satisfying the existing geometry/settings guards, not permission to trade drawing quality for throughput.

Run the repeated suite with `npm run --silent eval:routing:total-time > /tmp/routing-total-time.json`. It records seven samples per strategy/drawing after one excluded initial run, rotating strategy order between rounds. JSON retains medians, every sample, observed ranges, 1/10/100-copy totals, strict break-even counts, and hypothetical 5×/20× planning slowdowns. Those slowdowns are sensitivity scenarios, not measurements on other machines. To measure first-use computation without planning warm-up, start independent processes with `node tools/benchmark-routing-total-time.mjs --cold-once grid-17 search-all` (substitute drawing and strategy). `--check` runs the formula and settings self-checks alone.

Timing starts after source imports/building and fixture generation. SVG parsing, actual worker launch and message transit, UI rendering, HTTP encoding/network transport, and unmodelled device effects are excluded. Source bundling is only how the research harness loads current TypeScript; it is not a production planning charge. The local transfer/reconstruction measurement covers CPU work, not browser scheduling. Planning samples are measured wall time on this computer; plotting values remain Saxi motion-model estimates. Treat the reported sum as an estimate of sequential planning plus plotting, not a measured click-to-finished-paper latency. Choosing the winning recipe after trying everything still incurs the full portfolio cost.

Other targeted recipes avoid similar waste. The four-traversal method takes about **9.5 ms** on the connected grid for the same 47.57-second saving as the 156-ms full portfolio. The plain Euler recipe takes about **0.9 ms** on the loop chain for the same 6.19-second saving as the 24-ms portfolio. For the 300-contour example, direct iterated seam/direction search takes about **0.53 seconds** for the same 26.55-second saving as the 3.51-second portfolio. These examples preserve the earlier pen-contact preference; they do not achieve their savings by permitting extra marks.

Fresh-process measurements confirm that first-use computation matters, particularly for short jobs. Median full-search CPU time increases from 156 to 202 ms for the grid, 317 to 402 ms for 300 hatch lines, and 5.39 to 6.71 seconds for 2,000 hatch lines. The latter still finds no gain. For the large scattered drawing, five fresh runs per targeted method give medians of 1.38 seconds for direction refinement and 2.51 seconds for relocation, with enough variation to retain the cautious one-copy conclusion. These are fresh Node computations, not browser-worker start-up measurements.

Hypothetical slower planning also changes the decision. Multiplying all planning times by 20 moves the full scattered-drawing portfolio's break-even from two copies to 24, and the full 300-contour search from one to three. For the *targeted* relocation upgrade over direction refinement, the paired medians imply about five copies at 5× planning time and 20 copies at 20×. These factors intentionally isolate CPU sensitivity; they are not estimates for a particular Raspberry Pi, browser, or phone.

The production direction should therefore be:

1. Use drawing constraints and current settings to determine eligible operations first. Keep disabled joining, minimum-length filtering, preserved segments/dabs, and the preference for fewer pen contacts.
2. Choose a small search appropriate to the prepared drawing: continuity/traversal work for connected strokes, seam/direction work for closed contours, and bounded route refinement for disconnected strokes. Validate any automatic choice on drawings outside the tuning suite.
3. Budget additional search using expected copies and remaining possible savings, and make the search interruptible inside its expensive loops. An iteration cap alone is not a predictable wall-time cap. Falling back afterward cannot undo search time.
4. Reuse the result for a batch. In the existing UI this already works while drawing/settings remain unchanged. Separate CLI invocations do not amortize planning; they would need explicit plan reuse or a batch runner.

The interface should report estimated **planning plus plotting** for the intended copy count alongside pen-contact counts. It should allow the user to value a more continuous physical mark even when a small time saving is uncertain. No production optimizer, copy-count control, or automatic method selector was introduced by this timing study.
